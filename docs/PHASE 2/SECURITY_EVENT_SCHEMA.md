# ProShield — SecurityEvent Schema

## 1. Purpose

This document defines the canonical `SecurityEvent` contract used by the
ProShield MVP.

The `SecurityEvent` is the normalized representation of an observed
security-related event entering the ProShield processing pipeline.

It is the foundation for:

SecurityEvent
→ Detection
→ Correlation
→ Timeline
→ Severity + Confidence
→ Incident
→ Report
→ Routing

The canonical event must remain independent of any individual security
product.

This document defines the logical contract and the serialization rules
required by the MVP. Physical MongoDB collection details are documented
separately in the Phase 2 data-model work.

---

## 2. What a SecurityEvent Represents

A `SecurityEvent` represents an observed security-related event reported by
a source.

Examples:

- WAF detection
- blocked request
- rate-limit violation
- suspicious request
- authentication failure
- authentication success
- TLS anomaly
- network anomaly

A `SecurityEvent` is an observation.

It is NOT:

- a detection
- an incident
- a confirmed attack
- a severity decision
- a routing decision
- an analyst conclusion
- an AI-generated interpretation

Derived conclusions must be created by later ProShield processing.

---

## 3. Canonical Event Principle

All supported sources must ultimately produce the same canonical
`SecurityEvent` structure.

Source-specific architecture:

Source
→ Collector / Adapter
→ Canonical SecurityEvent
→ ProShield Core

The planned source progression is:

1. Simulator
2. NGINX
3. WAF / Cezara
4. Rate Limiting
5. TLS / Network
6. Future SIEM
7. Future Endpoint
8. Future IAM

The core detection and correlation engine must not contain source-specific
business logic.

---

## 4. Canonical JSON Representation

The canonical wire representation for a SecurityEvent is JSON.

A representative event is:

```json
{
  "event_id": "0198c2a1-7e3b-7a8e-b7b6-4f6a7d4d5f12",
  "event_time": "2026-08-26T03:15:42.123Z",
  "ingested_at": "2026-08-26T03:15:42.456Z",
  "source": "nginx",
  "event_type": "request_blocked",
  "source_ip": "192.0.2.10",
  "destination": "app.example.internal",
  "endpoint": "/api/login",
  "asset": "web-api-01",
  "account": {
    "id": "user-123"
  },
  "device": {
    "id": "device-456"
  },
  "details": {
    "http_method": "POST",
    "status_code": 403,
    "reason": "security_policy"
  },
  "provenance": {
    "collector": "nginx-adapter",
    "source_event_id": "nginx-998877"
  }
}
```

This example is illustrative.

The exact event-type-specific `details` structure may vary by event type,
but the common envelope must remain stable.

---

## 5. Required Canonical Fields

The following fields are required in the canonical model.

### 5.1 `event_id`

Unique identifier for the canonical ProShield security event.

Requirements:

- globally unique
- generated by ProShield when a canonical ID does not already exist
- immutable
- safe to reference from downstream objects

The MVP uses UUIDv7 for internal identifiers.

Example:

```text
0198c2a1-7e3b-7a8e-b7b6-4f6a7d4d5f12
```

A source-provided event ID remains separate from the canonical
`event_id`.

---

### 5.2 `event_time`

The time when the observed security event occurred according to the source.

Requirements:

- ISO 8601 / RFC 3339 representation
- UTC
- unambiguous timezone
- preserved from the source when available

Example:

```text
2026-08-26T03:15:42.123Z
```

---

### 5.3 `ingested_at`

The time ProShield received or accepted the event.

Requirements:

- generated by ProShield
- ISO 8601 / RFC 3339
- UTC

This must remain separate from `event_time`.

The difference can reveal:

- source delay
- network delay
- buffering
- collector delay

---

### 5.4 `source`

Identifies the source system that produced the event.

Initial examples:

- `simulator`
- `nginx`
- `waf`
- `rate_limiter`
- `tls`
- `network`

Future examples may include:

- `siem`
- `endpoint`
- `iam`

The source must be controlled by the collector/integration layer and must
not be freely trusted from arbitrary client input.

---

### 5.5 `event_type`

Identifies the observed security event type.

Initial supported event types:

- `waf_attack_detected`
- `request_blocked`
- `rate_limit_exceeded`
- `suspicious_request`
- `authentication_failure`
- `authentication_success`
- `tls_anomaly`
- `network_anomaly`
- `security_control_alert`

New event types require an explicit contract change.

---

## 6. Optional Canonical Fields

The following fields are optional because not every security event provides
them.

### 6.1 `source_ip`

Source/client IP associated with the event.

Used for:

- correlation
- investigation
- attack-pattern analysis

---

### 6.2 `destination`

Destination or target associated with the event.

Examples:

- hostname
- service
- destination address

---

### 6.3 `endpoint`

Application/service endpoint involved in the event.

Examples:

- `/login`
- `/api/users`
- service endpoint identifier

---

### 6.4 `asset`

The affected asset or protected resource when known.

Examples:

- web server
- application
- service
- network asset

Business criticality is not part of the raw event merely because an asset
has one.

Business criticality comes from an authorized asset/configuration source
when required by later severity/routing logic.

---

### 6.5 `account`

The account or identity associated with the event, when available.

Example:

```json
{
  "id": "user-123"
}
```

The exact identity model may be extended later.

This field must never contain:

- passwords
- password hashes
- access tokens
- private credentials

---

### 6.6 `device`

The relevant device when available.

Example:

```json
{
  "id": "device-456"
}
```

The exact device model is not yet expanded beyond the information needed
for correlation.

---

## 7. `details`

`details` contains structured event-specific information.

Examples:

```json
{
  "http_method": "POST",
  "status_code": 403,
  "reason": "security_policy"
}
```

or:

```json
{
  "threshold": 100,
  "observed_count": 145,
  "window_seconds": 60
}
```

Rules for `details`:

- must remain structured JSON data
- must have bounded size
- must be validated per event type where practical
- must not contain unrestricted executable expressions
- must not become an unbounded raw-text dump
- must not contain secrets

`details` exists to accommodate source/event-specific information without
changing the common canonical envelope for every new event type.

---

## 8. `provenance`

`provenance` records where the event came from and how it entered
ProShield.

It should support, when available:

```json
{
  "collector": "nginx-adapter",
  "source_event_id": "nginx-998877"
}
```

Possible future information may include:

- source connector version
- ingestion path
- source instance identifier
- transformation metadata

The exact structure may expand as real collectors are integrated.

---

## 9. Source Identity vs Canonical Event Identity

These are different concepts.

### `event_id`

The authoritative ProShield event identifier.

### `source_event_id`

The identifier provided by the originating system, when available.

Example:

```text
ProShield event_id:
0198c2a1-7e3b-7a8e-b7b6-4f6a7d4d5f12

Source event ID:
nginx-998877
```

They must not be assumed to be identical.

This separation supports:

- provenance
- duplicate detection
- reconciliation
- investigation
- debugging

---

## 10. Timestamp Rules

The canonical event distinguishes:

```text
event_time
=
when the source says the event occurred

ingested_at
=
when ProShield received the event
```

Both use UTC and RFC 3339 / ISO 8601 serialization.

The system must not assume that:

```text
event_time == ingested_at
```

Events may arrive late or out of order.

---

## 11. JSON Serialization Rules

### Timestamps

Use UTC RFC 3339 / ISO 8601.

Example:

```text
2026-08-26T03:15:42.123Z
```

Do not mix local time, epoch seconds, and epoch milliseconds inside the
same canonical contract.

---

### Enumerations

Use explicit string values.

Example:

```json
{
  "event_type": "rate_limit_exceeded"
}
```

Do not encode semantic enums as undocumented numeric codes.

---

### Optional Fields

An unavailable optional value should be:

- omitted, or
- explicitly `null` when the distinction is meaningful.

The system must not invent placeholder values such as:

```text
"unknown-ip"
"not-applicable"
"fake-user"
```

unless the schema explicitly defines such enumerations.

---

### Additional Fields

The canonical envelope is strict.

Unknown top-level fields should be rejected unless explicitly introduced
through a versioned contract change.

The `details` object is the controlled extensibility boundary for
event-specific information.

---

## 12. Input Size and Bounded Data

All event fields must have bounded sizes appropriate to their purpose.

There must be explicit protections against:

- oversized event payloads
- oversized `details`
- oversized strings
- excessive nesting
- event flooding

Exact numeric limits will be finalized with the API/security contract, but
the implementation must never rely on an assumption that incoming events
are small.

---

## 13. Validation

Before a SecurityEvent enters the trusted processing pipeline, it must be
validated.

Validation must cover:

- required fields
- event ID format
- timestamp validity
- event type
- source
- data types
- bounded lengths
- structured `details`
- provenance structure

Invalid events must not silently enter normal detection processing.

---

## 14. Normalization

Collectors convert source-specific structures into the canonical event
model.

Example:

```text
NGINX log
    ↓
NGINX Adapter
    ↓
Canonical SecurityEvent
```

Example:

```text
WAF event
    ↓
WAF Adapter
    ↓
Canonical SecurityEvent
```

Normalization may transform:

- field names
- timestamps
- enumerations
- types
- source metadata

Normalization must not invent security conclusions.

---

## 15. Duplicate Handling

ProShield must support duplicate-event handling.

Possible identifiers include:

- canonical `event_id`
- source + `source_event_id`
- explicitly defined source-specific deduplication keys

The system must distinguish:

```text
duplicate delivery
```

from:

```text
genuinely separate observations
```

The exact deduplication policy will be finalized in implementation and
query design.

---

## 16. Replay Considerations

A previously valid event received again must not automatically become a
new observation.

Replay protection may use:

- event identity
- source identity
- source event identity
- event timestamps
- defined replay windows

The final technical implementation must satisfy the Phase 1 threat model.

---

## 17. Event Ordering

Events may arrive:

- in order
- out of order
- delayed
- in batches

The ingestion order must not be treated as the authoritative event order.

Timeline and correlation logic must use `event_time` and the defined
ordering policy.

---

## 18. Unknown Events

A valid event may not match any current detection rule.

That is not an error.

Expected behavior:

- preserve the event
- do not fabricate a detection
- do not fabricate an incident
- do not invent an attack category
- keep the event available for future rules or human review

Unknown does not mean malicious.

---

## 19. Security Data Separation

The following must remain outside the raw SecurityEvent unless the source
explicitly provides a source-level observation and the contract permits it:

- final incident severity
- final classification
- routing recommendation
- analyst assignment
- human decision
- recommended response
- confirmed breach declaration
- AI interpretation

Derived security intelligence belongs in downstream domain objects.

---

## 20. Sensitive Data Restrictions

SecurityEvents must never contain:

- plaintext passwords
- access tokens
- refresh tokens
- private keys
- API secrets
- database credentials
- production secrets

Sensitive source information must be minimized.

If a source contains sensitive data that ProShield does not need, the
collector should remove or transform it before the event enters the
canonical pipeline.

---

## 21. MongoDB Persistence Model

MongoDB is the chosen primary persistence layer for ProShield.

Canonical SecurityEvents are stored in the `security_events` collection.

The collection should preserve:

- canonical event fields
- provenance
- structured details
- timestamps
- event identity

MongoDB document storage is appropriate because event-specific metadata can
vary between sources.

However, the canonical top-level contract remains structured and bounded.

The system must not use MongoDB flexibility as an excuse to store arbitrary
unvalidated documents.

---

## 22. MongoDB Integrity Requirements

The persistence layer should enforce, where practical:

- unique `event_id`
- appropriate indexes
- schema validation
- bounded payloads
- protected database credentials
- authorized access
- timestamp/query indexes

Security-event writes must be performed through controlled backend
services rather than directly by untrusted clients.

---

## 23. Indexing Requirements

The initial `security_events` collection should support likely queries such
as:

- events by `event_time`
- events by `source`
- events by `event_type`
- events by `source_ip` when available
- events by asset
- events by account when available
- events by provenance/source-event identity

Exact compound indexes should be finalized when API/query requirements are
implemented.

---

## 24. Retention

Security events are high-volume data.

The initial production-MVP retention policy should therefore be configurable.

Default MVP target:

```text
SecurityEvents: 90 days
```

This is a starting operational policy, not a legal or regulatory claim.

A deployment may choose a different retention period based on:

- customer requirements
- contractual requirements
- regulatory requirements
- storage capacity
- incident-investigation requirements

Retention changes must be explicit and auditable.

---

## 25. Archival and Purge

Security events should follow a controlled lifecycle:

```text
Active
  ↓
Retained
  ↓
Archived where required
  ↓
Controlled purge
```

Application code must not permit arbitrary unaudited deletion of retained
security evidence.

Purge behavior must follow configured retention policy.

---

## 26. Internal ID Format

Internal canonical entity IDs use **UUIDv7**.

For SecurityEvent:

```text
event_id = UUIDv7
```

Reasons:

- globally unique
- server-generated
- suitable for distributed generation
- naturally sortable by creation time
- avoids sequential identifiers exposing record counts

Human-readable display IDs may be added later, but they are not the
authoritative event identity.

---

## 27. Message Envelope

When SecurityEvents travel through internal asynchronous processing or
integration boundaries, they should use a versioned JSON envelope.

Conceptual structure:

```json
{
  "message_id": "0198c2a1-8b10-7a2e-91e1-3e5b5d4c9a21",
  "message_type": "security_event",
  "schema_version": "1.0",
  "occurred_at": "2026-08-26T03:15:42.123Z",
  "source": "nginx",
  "payload": {
    "event_id": "0198c2a1-7e3b-7a8e-b7b6-4f6a7d4d5f12"
  }
}
```

The message envelope is separate from the SecurityEvent itself.

---

## 28. Message Delivery Principle

The architecture should assume:

```text
at-least-once delivery
+
idempotent processing
```

It must not depend on an assumption of perfect exactly-once delivery.

Every message has a `message_id`.

Consumers should protect against duplicate delivery where the operation is
not naturally idempotent.

The exact transport is not yet locked.

Possible future transports may include:

- HTTP
- lightweight internal queue
- message broker

The transport decision will be based on actual workload and deployment
requirements.

---

## 29. Schema Versioning

The canonical SecurityEvent contract must have an explicit schema version
when transported or persisted in a context where evolution matters.

Example:

```text
schema_version = "1.0"
```

A backwards-incompatible change must create a new version.

The meaning of an existing field must not silently change under the same
schema version.

---

## 30. Rule Relationship

A SecurityEvent is input evidence to the Rule Engine.

The rule does not become part of the SecurityEvent.

The relationship is:

```text
SecurityEvent(s)
      ↓
Rule Evaluation
      ↓
Detection
```

The Detection must record which rule ID/version produced it.

---

## 31. Downstream Relationship

A SecurityEvent may contribute to:

- zero or more detections
- one or more correlations
- one or more timeline entries
- one or more incidents, subject to correlation/lifecycle rules

The event remains the authoritative observation.

Downstream objects should reference the event rather than duplicate the
entire event payload unnecessarily.

---

## 32. API Representation

When returned through an API, a SecurityEvent must be serialized through an
explicit response schema.

The API must not automatically expose:

- internal storage metadata
- database implementation details
- privileged source credentials
- secret fields
- internal processing information

Authorization controls which event data a caller may see.

---

## 33. Test Requirements

The SecurityEvent contract must have tests for:

### Valid event

Valid canonical event is accepted.

### Missing required field

Event is rejected.

### Invalid event type

Event is rejected according to the supported event catalogue.

### Invalid timestamp

Event is rejected.

### Invalid types

Event is rejected.

### Oversized input

Event is rejected safely.

### Duplicate delivery

Duplicate behavior follows the defined policy.

### Replay

Replay handling follows the security policy.

### Provenance

Source and source-event identity remain traceable.

### Sensitive data

Secrets cannot enter the canonical event.

### Serialization

The same valid event produces a predictable canonical JSON structure.

### Normalization

Different source formats map correctly into the canonical event.

---

## 34. Compatibility Requirements

A new collector should require primarily:

1. collector implementation
2. source-to-canonical mapping
3. source-specific validation
4. source-specific tests

It should not require rewriting:

- detection
- correlation
- timeline
- incident management
- report generation
- routing

unless the new source introduces a genuinely new capability that requires
an explicit architecture decision.

---

## 35. Explicitly Not Part of This Contract

This SecurityEvent schema does not define:

- Detection schema
- Correlation schema
- Incident schema
- Report schema
- Routing schema
- Audit schema
- API endpoint definitions
- final rule DSL
- final routing policy schema

Those are separate Phase 2 contracts.

---

## 36. Final Contract Principle

The canonical SecurityEvent must remain:

- small enough to understand
- structured enough to validate
- flexible enough for multiple security sources
- bounded enough to protect ProShield
- traceable enough for investigation
- stable enough for downstream processing
- independent enough for future integrations

The fundamental rule is:

> **A SecurityEvent records what the security environment observed. ProShield
> derives everything else from those observations.**
